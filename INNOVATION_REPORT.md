# Innovation and limits

FLOWCORE's contribution in this slice is a coordination protocol between existing Linux actuators and application observations. This is an incremental integration result. Linux already provides shaping, queue management, congestion control, pacing and multipath mechanisms.

| Technical limitation | Existing Linux mechanism | Integrated experiment | Evidence and remaining limit |
|---|---|---|---|
| A class controller and a socket controller can retain incompatible active constraints | HTB controls class rates and borrowing. A TCP socket pacing cap limits that sender independently. | The pacing worker requires a fresh kernel-verified HTB baseline and exclusive adaptive authority. Capacity transitions carry a generation. The worker verifies restoration of its nonbinding cap when scope changes. | Socket readback and the transition journal show verified actions and compensation. The cooperating workload owns the socket. A hostile privileged actor remains outside the trust boundary. |
| Kernel congestion signals alone do not carry the application's deadline or failure denominator | TCP_INFO and ECN expose transport observations. AQMs respond to queue state and ECN negotiation. | The planner combines scoped AQM/TCP evidence, measured pressure and application deadline proximity. The raw ledger retains every offered attempt and ties it to a declared budget. | Deadline and ECN signals are operational evidence. The full-system comparison changes several planner inputs together, so it does not identify their individual contributions. |
| A successful kernel write can harm a service or bulk progress | getsockopt verifies an installed socket cap. It cannot report user-visible latency or class fairness. | Outcome windows check application P99 and measured aggregate background progress. Failed group writes compensate earlier writes and read back the cohort. | The native fixture verifies adverse-outcome rollback. Live socket decisions and compensation remain scoped to one cohort and lab. |
| Capability declarations can outlive working kernel behavior | Kernel configurations, sysctls and BPF object files expose support indications. Runtime readback or negotiated transport can supply stronger evidence. | Capability inventory records the observed proof and its scope. The pacing path uses timestamped live policy verification. | Build, connection, namespace and service evidence remain separate. No cross-host control or eBPF attachment is inferred from a build probe. |

The integration and its measurement method are reproducible with [Next-generation benchmarks](NEXTGEN_BENCHMARKS.md). The experiments do not establish a new kernel mechanism or general superiority over standalone Linux. In particular, ordinary ECN, class-aware traffic control and independently paced sockets are established mechanisms.
