# Kernel upstream decision

Keep this experiment in userspace and stock TC. The reproduced shared-flow problem is expressible using Linux's existing per-datagram hints and queue classes. The experiment has not established a missing scheduler mechanism with a measurable benefit against the strongest stock alternative. There is no kernel RFC or patch series for this result. [Benchmark evidence](SCHEDULER_BENCHMARKS.md)

## Evidence required to reopen

- Demonstrate a workload where a bounded, authenticated packet intent cannot be expressed through existing priority, TC classification, CAKE tins or the transmit-time interfaces. Compare against the best applicable configuration at the same bottleneck. An ordered stream delivery dependency and a remote network bottleneck belong outside the local qdisc claim.
- If the open question is a different queue-selection algorithm, prototype it first using the existing BPF Qdisc_ops interface in a disposable VM. Compare deadline attainment, failure and fairness under frozen budgets and paired scenarios. Measure CPU and memory under flow churn and induced queue overflow. [BPF qdisc code](https://github.com/torvalds/linux/blob/master/net/sched/bpf_qdisc.c) · [BPF qdisc kselftest](https://github.com/torvalds/linux/blob/master/tools/testing/selftests/bpf/prog_tests/bpf_qdisc.c)
- Consider a kernel addition only if that path exposes a concrete missing primitive. Document its scope, privilege, resource accounting, namespace lifetime, compatibility, drop policy and failure behavior. Keep new packet metadata separate from TCP request framing. Validate enqueuing, dequeue, reset, watchdog, graft and concurrent teardown with focused kselftests. Use verifier and fault-injection coverage for BPF changes. [Kselftest guidance](https://docs.kernel.org/dev-tools/kselftest.html)
- If code eventually needs testing on a new kernel, use a disposable guest with an offline snapshot and an independently bootable stock kernel. Keep results and workload definitions off the guest before restoring it. No host kernel or boot configuration was changed for the current study.

Scheduling and TC patches generally go through netdev and the appropriate networking tree. Changes to a BPF qdisc hook or helper also need BPF review. Determine recipients and prefixes from the actual target revision and diff, consult recent related work, and include a minimal reproducer, comparative results and selftests. Use the tree's maintainer and checkpatch scripts, and follow its submission and DCO requirements.
